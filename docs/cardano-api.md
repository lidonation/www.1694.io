# Cardano on-chain data gateway

The API backend and queue workers use infrastructure's Blockfrost-compatible
`/api/v0` interface. They retain `BlockfrostService` as the compatibility boundary
so governance payloads, lovelace precision, pagination, UTXOs and CBOR submission
are unchanged. The native Koios `/api/v1` API has different response shapes and
must not be substituted as the base URL.

## Cluster routing and credentials

| Environment | Helm `cardanoApi.network` | `CARDANO_API_URL` (generated by Helm) |
| --- | --- | --- |
| Preview | `preview` (default) | `http://koios-gateway-preview-koios-gateway.koios-gateway.svc.cluster.local/api/v0` |
| Production | `mainnet` (`values.prod.yaml`) | `http://koios-gateway-mainnet-koios-gateway.koios-gateway.svc.cluster.local/api/v0` |

These namespace-qualified Services bypass the public per-IP gateway quota.
This does **not** remove Koios/hosted Blockfrost upstream quotas, outages or
charges. Do not use `cardanoapis.2lovelaces.com` or
`preview-cardanoapis.2lovelaces.com` for indexing. HTTP/1.1 works on the internal
listener; h2c is supported by the gateway but is not required by these clients.

Both app containers explicitly reference `CARDANO_API_PROJECT_ID` in
`www-1694-backend-secrets` and the generated URL. Explicit `env` wins over stale
values in any `envFrom` Secret. The frontend does not load this Secret.

**Before deploying**, add `CARDANO_API_PROJECT_ID` to the environment-scoped
`ENV_FILE_BACKEND` CI file variable. Its value must be that network gateway's
client project ID (infrastructure vault key
`koios_gateway_preview_client_project_id` or
`koios_gateway_mainnet_client_project_id`), not a hosted Blockfrost project ID,
Koios JWT, or the gateway's own upstream credential. Use the normal authorized
secret-management process; never put the value in an MR, chart values or chat.
Do not put this key in frontend/global/queue env files. No new CI variable
outside the existing backend env file is needed. A missing key prevents the
app containers from starting; an empty key fails client initialization.

The first upgrade must be the full application deployment with the current
values files, not an indexer-only `--reuse-values` upgrade. An old release lacks
`cardanoApi.network` and gets an actionable rendering error. For credential
rotation, update the backend env file, deploy its Secret, and roll both app
Deployments so their environment variables reload.

## Local compatibility and fallback

Outside Helm, set `CARDANO_API_URL` and `CARDANO_API_PROJECT_ID` together. The
clients trim surrounding whitespace and trailing URL slashes. The URL must be
an absolute HTTP(S) base URL without embedded credentials, a query or a fragment;
invalid URLs fail at startup without logging their contents. Supplying only
one is a startup error, never an invitation to reuse another provider's key.
If both are absent, existing local `BLOCKFROST_NETWORK_URL` and
`BLOCKFROST_NETWORK_PROJECT_ID` still select the primary.

`BLOCKFROST_NETWORK_URL_FALLBACK` and
`BLOCKFROST_NETWORK_PROJECT_ID_FALLBACK` are unchanged. Verify they point at the
same network before rollout. The indexer continues comparing primary and
fallback epochs before stake updates, refuses a lagging/invalid primary and
tolerates an unreachable comparison source. Its not-found and retry policies
are unchanged. Heavy sync jobs remain incremental; bypassing public quota
is not a reason to force a full reindex.

IPFS is not on-chain data. The API's IPFS service and the queue's external
Blockfrost IPFS endpoint keep separate credentials. The queue still supports
its legacy Blockfrost key when `BLOCKFROST_IPFS_PROJECT_ID` is absent, but never
uses the new gateway key for IPFS. Prefer setting the IPFS key explicitly.

## db-sync audit

There is no active direct db-sync connection in the current `dev` branch.
`CardanoRepository` uses the default application data source and local indexed
governance entities; those cache queries must remain local. The old
`DbSyncUTXO` interface and unused `transformDbSyncUtxos` converter are not live
queries. The legacy CI `DEPLOY_CARDANO_DBSYNC` switch is unrelated deployment
history. This MR does not delete infrastructure or change the local schema.

## Verification and rollout gate

Infrastructure's [gateway runbook](https://gitlab.2lovelaces.io/2lovelaces/infrastructure/-/blob/main/wiki/runbooks/koios-gateway.md)
still labels compatibility/readiness unverified. Do not treat this MR or a pod
health check as proof of live service compatibility. No deployment or live
secret access was performed for this refactor.

1. From an authorized in-cluster diagnostic client, resolve the chosen Service
   and call `/health` on the Service root (without `/api/v0`).
2. Using the gateway client key securely, request `/api/v0/genesis`: mainnet's
   `network_magic` must be `764824073`, preview's `2`. A missing/incorrect key
   must return 403; being internal bypasses quota, not authentication.
3. Check `/api/v0/epochs/latest`, `/api/v0/blocks/latest`,
   `/api/v0/epochs/latest/parameters`, a known DRep and a known address's UTXOs.
   Verify real governance amounts, recent tip/epoch, pagination, and that the
   `project_id` sent is the gateway key. Do not log the credential.
4. Exercise fallback and the stale-primary guard in preview before production;
   do not replay real transactions merely to test submission.
5. Trigger manual `app-preview` with `DEPLOY_WEBSITE=true`, inspect API health
   and one incremental worker sync, then use the normal reviewed promotion and
   manual `production` deployment. Never force a full sync as a smoke test.

Local deterministic checks (no credentials or external chain calls):

```sh
(cd backend && yarn test --maxWorkers=6 && yarn build)
(cd queue-backend && yarn test --maxWorkers=6 && yarn build)
sh ci/tests/chart-cardano-api.test.sh
```

The Helm regression is part of the existing `test_deploy_config` CI job.
